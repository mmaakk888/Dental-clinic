# تحديث النظام — حزم موقّعة وحفظ البيانات

## للمستخدم: الخطوات المعتادة

1. نزّل نسخة كاملة مشفرة من «النسخ الاحتياطي والنقل»، واحفظها خارج الاستضافة ومفتاح فكها منفصلًا. اختر وقتًا لا يجري فيه تسجيل مرضى أو تحصيل.
2. افتح لوحة التحكم ← **تحديث النظام** بحساب المدير، خارج وضع الخصوصية وبعد حسم أي عملية مالية معلقة.
3. ارفع ملف `clinic-update-….zip` الذي سُلّم لك لهذا التطبيق، وأدخل كلمة سر المدير، ثم «فحص الحزمة ومعاينتها». لا ترفع ZIP المصدر أو SQL أو نسخة البيانات.
4. راجع إصدار البداية والنهاية والملاحظات، واكتب «تحديث النظام»، ثم ابدأ. ترى تقدمًا فعليًا بحسب الملفات والمراحل، وليس مؤقتًا شكليًا. أبقِ الصفحة مفتوحة لتنفيذ الطلبات المتتابعة.
5. بعد نجاح فحص تشغيل PHP والبيانات اضغط «تحميل الواجهة الحالية». الحفظ يُفتح بعد نجاح الفحص فقط. تبقى الإعدادات والحسابات وأرقام الملفات والصور والأرصدة كما هي.

لا توجد جدولة أو عملية خلفية مضمونة هنا. إذا أُغلق المتصفح أو انقطع الاتصال، يحفظ الخادم المرحلة. افتح الصفحة وحدّث الحالة ثم تابع؛ لا تكرر الرفع أو تثبّت حسابًا جديدًا.

## أول تركيب لهذه الميزة على إصدار قديم

الإصدار `php-mysql-3-backup` وما قبله لا يحتوي صفحة التحديث. **لا يمكن رفع ملف تحديث من صفحة غير موجودة.** ثبّت ملفات الإنتاج `clinic-htdocs.zip` مرة واحدة بالطريقة اليدوية أدناه، مع بقاء قاعدة البيانات وملف الاتصال الحاليين. هذا الإصدار لا يحتاج استيراد SQL جديد ولا مُثبّتًا جديدًا. بعدها تُستخدم الصفحة للتحديثات التالية.

حزمة هذا الإصدار `clinic-update-v4-v5-v6-v7-v8-to-v9.zip` موقّعة وموجهة إلى `php-mysql-4-updates` أو `php-mysql-5-unfiled` أو `php-mysql-6-workflow` أو `php-mysql-7-clean-paths` أو `php-mysql-8-interface`. تحتفظ بإصلاحات رحلة المريض والمعامل والروشتات، وتوحّد إغلاق النوافذ وحماية المسودات وتحسّن وضوح الأرقام والماليات داخل التصميم المعتمد. لا ترفعها فوق v9 المثبت بالفعل أو v3؛ فحص التوافق يرفض إعادة الإصدار نفسه أو إصدار بداية آخر. تفاصيل الاستخدام في WORKFLOW.ar.md، وهوية التوقيع لم تتغير.

## عند الفشل أو توقف الصفحة

- الحفظ يتوقف على السيرفر أثناء الصيانة، حتى لو حاول جهاز آخر تسجيل دفعة. عمليات بدأت قبل الصيانة تنتهي أولًا داخل قفل المراجعة.
- يحتفظ المجلد الخاص `clinic-private/system-updates` بنسخة مشفرة من قاعدة البيانات، متضمنة صور MySQL والمرفقات والحسابات والإعدادات، وصور الملفات التي ستُستبدل. التشفير المحلي مربوط بمفتاح `app_key` الحالي؛ لا تغيّره أثناء تحديث أو إنقاذ.
- فشل خطوة ملفات/ترحيل/فحص تشغيل يبدأ الرجوع. عند «استُعيد الإصدار السابق» يمكن متابعة العمل. إذا ظهر «لم نؤكد الاستعادة» تظل الصيانة مغلقة؛ لا تبدأ مُثبّتًا ولا تحذف هذا المجلد أو تستبدل قاعدة التشغيل.
- احفظ رابط الإنقاذ: `https://YOUR-DOMAIN/api/update.php?console=1`. يعمل بموزّع ثابت ومحرك إنقاذ خاص من الإصدار السابق، حتى لو تعطّل `core.php` أو `auth.php` الجديدان. يتطلب حساب مدير وCSRF وكلمة السر للرجوع. منه يمكن المتابعة أو الرجوع. ليس بابًا بلا تسجيل دخول.
- إذا تعذر HTTP ولديك Terminal، ارفع أداة الإنقاذ خارج htdocs وشغّل:

```sh
php /private-tools/update-recover.php /path/clinic-private/config.php /path/htdocs --rollback
```

أداة الإنقاذ تستخدم إعدادات الاتصال الحالية؛ لا تنقل أسرارًا من حزمة التحديث. إذا لم يوجد Terminal، اطلب من الدعم تشغيل الأمر أو استعادة ملفات الكود ونسخة SQL الخاصة بطريقة مدروسة. لا يُعد زر الرجوع وسيلة لإعادة قاعدة قديمة بعد نجاح التحديث وتسجيل معاملات جديدة؛ النظام يمنع ذلك.

## توافق الاستضافات والبديل اليدوي

الاستضافة **لم تُختر بعد**؛ ما اختُبر محليًا ليس شهادة توافق مع مزود بعينه. الصفحة تفحص PHP8.2+ وZipArchive وsodium وملف الإصدار ومساحة أولية وOPcache وكتابة ملفات التطبيق ومجلد خاص قابل للكتابة **خارج جذر الويب**. ويجري فحص كل مسار والمساحة اللازمة عند المعاينة. قد تظهر قيود إضافية في `open_basedir` أو وقت PHP أو صلاحيات ALTER؛ تُعرض نتيجة الفشل ولا نعرض نجاحًا وهميًا.

إذا كانت الاستضافة لا تسمح بالمجلد الخاص خارج htdocs أو الكتابة أو Zip/sodium، يبقى تحديث الملفات يدويًا. لا تُضعف الحماية بوضع نسخ قاعدة البيانات في مجلد عام أو صلاحيات777. لا يحتاج التحديث cron أو Webhooks أو Node.js على الاستضافة.

### أبسط تحديث يدوي

1. خذ نسخة SQL كاملة خاصة من phpMyAdmin، ونسخة ملفات الموقع والإعداد الخاص. فعّل صيانة من مدير الاستضافة؛ أوقف الحفظ على جميع الأجهزة. إذا لم توجد أداة صيانة، امنع دخول التطبيق مؤقتًا من إعداد الدومين/المجلد بعد حفظ نسخة إعداداته، وابقَ على phpMyAdmin/File Manager للإجراء.
2. فك **حزمة نشر موثوقة من المصدر** `clinic-htdocs.zip` على جهازك، وارفع محتوياتها إلى htdocs/public_html مع استبدال ملفات التطبيق فقط. لا ترفع المصدر أو SQL أو المفاتيح الخاصة. لا تلمس `clinic-private/config.php` أو `defaults.json` الحاليين أو مجلد النسخ. الصور الحالية مخزّنة داخل MySQL ولا تحتاج حذفًا أو إعادة رفع.
3. اتبع ترحيل الإصدار المرفق إن وُجد، على قاعدة تجربة أولًا ثم التشغيل بعد نسخة أمان. **لا تستورد schema.sql من جديد على قاعدة قائمة.** هذا الإصدار v9 لا يحتاج تعديل مخطط الجداول الحالي؛ البيانات والإعدادات باقية في الجداول نفسها.
4. أعد تشغيل PHP/امسح OPcache من اللوحة إن لزم، وافتح الموقع من نافذة جديدة، واختبر الدخول ومريضًا ومرفقًا والأرصدة دون إنشاء دفعات حقيقية للاختبار، ثم ألغ الصيانة. إذا فشل: أبقِ الحفظ مغلقًا، وأعد ملفات الكود ونسخة SQL المأخوذة قبل التحديث، ثم تحقق وأعد الفتح.

قبل اختيار استضافة اسألها عن مجلد خاص خارج public_html، ZipArchive، sodium، رفع ZIP بحجم الحزمة، كتابة/rename وflock، ووقت PHP ومساحة النسخ. على الخادم الفعلي يجب اختبار حماية الملفات الخاصة وHTTPS ورفع الحزمة وفحص التشغيل بحسابك.

## ما تسمح به ترحيلات قاعدة البيانات الداخلية v1

لا تنفّذ الصفحة SQL أو ملفات PHP للترحيل من داخل ZIP. تدعم ترحيلات وصفية موقّعة: إضافة إعداد فني افتراضي دون استبدال قيمة قائمة، وإضافة عمود nullable بأنواع محدودة إلى جداول التطبيق الحالية. قبل ALTER يُكتب قصد الرجوع أولًا؛ عند الفشل يُزال **العمود الذي أضافته هذه المحاولة فقط** وتُستعاد النسخة داخل معاملة SQL. أوامر MySQL البنيوية قد تُجري commit ضمنيًا، لذلك لا نعتمد على PDO rollback وحده.

حذف/إعادة تسمية جداول أو أعمدة، تغيير نوع قائم، SQL حر، أو تغيير schemaVersion الرئيسي، أو تحديث موزّع الإنقاذ الثابت `api/update.php` وملفيه `update-console.js/css`: يرفضها المسار الداخلي. تحتاج إصدارًا ودليل ترحيل يدويًا منفصلًا واختبار رجوع، ولا تُحذف الوظيفة أو تُتجاهل الترحيلات بصمت. واجهة الإنقاذ بملفات خارجية متوافقة مع سياسة CSP الأساسية، ولا تعتمد على inline JavaScript المحظور على Apache.

[مرجع MySQL للـ implicit commit](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html).

## للمطور: إصدار حزمة التحديث التالية

كل تحديث له إصدار جديد في `portable/api/version.php`، ويبنى من نفس مصدر الواجهة المعتمد. لا يُغيّر رقم إصدار عشوائيًا ولا يعاد تغليف ZIP المصدر باعتباره تحديثًا.

```sh
pnpm lint
pnpm test
pnpm test:api
pnpm test:updates
# انقل مجلدَي الإصدار السابقين إلى نقطة رجوع قبل البناء؛ لا تكتب فوقهما.
pnpm build
pnpm package:update build/portable-release/htdocs /OFFLINE/publisher.private.pem php-mysql-9-settings-scroll build/portable-artifacts/clinic-update-next.zip [migrations.json]
```

توليد مفتاح توقيع جديد يتم مرة واحدة فقط بـ `pnpm package:update keygen /OFFLINE/publisher.private.pem`، ثم تثبيت **المفتاح العام** في `portable/api/update-trust.json` قبل إصدار أول نسخة. للمشروع الحالي وُلدت هوية توقيع محفوظة محليًا خارج المصدر؛ احتفظ بملفها الخاص خارج الاستضافة وبنسخة مشفرة منفصلة خارج اللاب. هذا مفتاح توقيع الإصدار، وليس مفتاح فك نسخ المرضى. لا ترفعه إلى GitHub أو htdocs أو الحزم، ولا تولّد بديلًا في كل تعديل؛ لن تثق النسخ المثبتة بالمفتاح البديل.

الحزمة تُوقّع Ed25519 على بايتات البيان، وتضم SHA256/حجم كل ملف وإصداري البداية والنهاية. المستقبِل يتحقق قبل نسخ المحتوى، ويرفض traversal والروابط الرمزية والملفات المكررة/الزائدة ونسب الضغط العالية والحزم غير المتوافقة. يوجد قفل `flock` ومحاولة نشطة واحدة، وفحص نسخة الملفات مرة أخرى قبل البدء. مفتاح توقيع مسروق يعادل ناشرًا مخترقًا؛ لا تسمح بمشاركة الملف الخاص.

تطبيق يدوي دون التوقيع الداخلي لا يصبح موثوقًا تلقائيًا؛ استعمل فقط ZIP إنتاج وصل من مصدر المشروع الموثوق، وقارن SHA256 خارج الموقع إن وُجد.
